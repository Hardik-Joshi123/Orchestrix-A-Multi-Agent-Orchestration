# Task 12: LLM Planning Quality and Plan Validation Report

## Executive Summary

Task 12 focused on improving the reliability, structural integrity, and decomposition quality of execution plans generated by the multi-agent orchestrator's supervisor. Prior to this task, while dynamic planning allowed LLM completions to influence specialist selection, the orchestrator lacked formal validation of generated plans. As a result, malformed JSON, unsupported specialist names, duplicate subtask IDs, self-dependencies, dangling prerequisite references, dependency cycles, and runaway oversized plans could cause runtime failures or uncoordinated executions.

All requirements for Task 12 have been implemented and verified:
1. **Plan Schema & Semantic Validation:** Implemented `validate_plan` in `src/orchestrator/graph/supervisor.py` to enforce non-empty subtask descriptions, supported specialist mapping, unique stable subtask IDs, valid dependencies without self-references, acyclic graph structure (via topological sort), and plan size bounding (`MAX_PLAN_SIZE = 10`).
2. **Safe Handling of Invalid Plans:** Updated `supervisor.decompose` to validate LLM-generated plans strictly. If an LLM returns malformed JSON, unsupported specialists, duplicate IDs, missing dependencies, or cycles, the plan is safely rejected and the supervisor falls back to validated keyword-based planning. If even the fallback plan cannot be validated, execution yields a controlled failure (`status: "failed"`) without crashing.
3. **Improved Planning Quality & Prompts:** Enhanced the supervisor decomposition prompt with clear specialist responsibilities (`research`, `analysis`, `code`, `writing`), instructions to generate the minimum necessary subtasks (1–4), genuine prerequisite dependencies only, and empty dependencies (`depends_on: []`) for independent subtasks.
4. **Preserved Compatibility:** Preserved custom injected plan execution via `run_task(task, plan=...)`, existing dependency-aware execution, HITL escalation, memory integration, tracing/observability, and CLI JSON purity.
5. **Testing & Verification:** Added 9 new unit and integration tests in `tests/test_planning.py` (totaling 19 tests, 100% passing). The full repository test suite passed with 168 passing tests and 0 failures.

## Issues Addressed & Implementation Details

### 1. Plan Schema Validation (`validate_plan`)
In `src/orchestrator/graph/supervisor.py`, introduced `validate_plan(plan, strict_specialists=True, max_size=MAX_PLAN_SIZE)`:
- **Non-emptiness & Size Bounding:** Verifies that the plan is a non-empty list of dictionaries and does not exceed `MAX_PLAN_SIZE` (10 subtasks).
- **Subtask ID Uniqueness & Stability:** Asserts that every subtask has a non-empty `id` string and that no duplicate IDs exist in the plan.
- **Actionable Descriptions:** Ensures every subtask has a non-empty, stripped `instruction` string.
- **Supported Specialist Mapping:** Under `strict_specialists=True` (used for LLM plans), verifies that the subtask's `kind` matches either `VALID_SPECIALISTS` (`research`, `analysis`, `code`, `writing`) or recognized aliases (`coder`, `developer`, `writer`, `analyst`, etc.).
- **Dependency Soundness:** Checks that no subtask depends on itself (`sid in deps_list`), and that all declared dependencies exist in the plan's declared subtask IDs.
- **Cycle Detection:** Employs Kahn's algorithm (topological sort via in-degree tracking) to detect circular dependencies across the entire plan. If visited nodes in topological order are fewer than the total number of subtasks, a dependency cycle is flagged and rejected.

### 2. Plan Payload Parsing & Bounding (`parse_plan_payload`)
In `src/orchestrator/graph/supervisor.py`:
- Added automatic plan bounding: if the payload contains more than `max_size` items, it is sliced to `max_size` items.
- Added dependency deduplication (`list(dict.fromkeys(depends_on))`) to eliminate duplicate prerequisite declarations without altering dependency order.
- Supported `strict_specialists` parameter: when `True`, returns `None` immediately if an unsupported specialist is encountered, facilitating clean fallback.

### 3. Decomposition Logic & Graceful Fallback (`decompose`)
In `src/orchestrator/graph/supervisor.py`:
- **Injected Plan Handling:** If `state["plan"]` is provided by the caller (e.g. in test suites testing diamond dependencies or custom specialist ordering), it is parsed and used directly, preserving `test_dependencies.py` and caller contracts.
- **LLM Generation:** LLM completion is parsed with `strict_specialists=True` and validated via `validate_plan`. If valid, it is adopted (`plan_source = "llm"`). If invalid or unparseable, it is logged and rejected.
- **Fallback Planning:** If no LLM plan is available or the LLM plan was rejected, `plan_subtasks(task)` generates the keyword-based plan. This fallback plan is also validated with `validate_plan`.
- **Controlled Failure:** If neither LLM planning nor keyword fallback produces a valid plan (e.g., if fallback was corrupted or task is unexecutable), `decompose` returns a failed subtask in state with `status="failed"` and diagnostic error metadata. The orchestrator's graph transitions to `reduce` and yields a controlled failure without unhandled exceptions or crashes.

### 4. Planning Quality & Prompt Enhancement
Updated the supervisor prompt to guide LLMs toward concise, modular plans:
- Clear capability mappings for `research`, `analysis`, `code`, and `writing`.
- Explicit instructions to decompose into the minimum necessary subtasks (1–4), avoiding redundant or near-duplicate subtasks.
- Strict directive to set `depends_on` only when a genuine prerequisite output is needed, ensuring independent subtasks have `depends_on: []` to enable independent execution.
- Instruction to specify unique IDs (`s1`, `s2`, ...) and avoid self-dependencies or cycles.

## Limitations and Unverified Behavior

1. **Mock vs. Live LLM Providers:** Tests rely on mock LLM completions (`LLMClient.complete` mocked or returning mock text) and offline in-process execution. Live provider API roundtrips (e.g. OpenAI / Anthropic) were not invoked to respect offline and zero-cost constraints.
2. **Subtask Granularity:** Subtasks are bounded to `MAX_PLAN_SIZE = 10`. Extremely broad tasks requiring more than 10 separate steps will be bounded to the first 10 subtasks.
3. **Complex Semantic Redundancy:** Near-duplicate instructions with different phrasing (e.g. "Draft the document" vs "Write up the text") rely on LLM adherence to system prompt instructions, while exact duplicates are pruned.
